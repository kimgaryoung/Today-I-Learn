# 1. Inline

: 네트워크 상의 데이터 패킷이 반드시 해당 장치를 통과하도록 설계된 네트워크 구조.

### 1-1 워밍업 : 네트워크 장비는 어디에 놓이느냐가 중요하다

- 네트워크 장비 + 네트워크 기초 개념.
- 트래픽 흐름상 이 장비가 어디에 놓이는지도 중요.
- 보안 장비는 사용자의 요청이 서버로 가는 길목에 있음.

### 1-2 특징

1. <span style="color:red">**반드시 지나간다.**</span> : **트래픽이 인라인 장비를 우회할 수 없음.**
2. <span style="color:red">**트래픽을 직접 제어한다.**</span> 인라인 장비는 트래픽을 항상 지나가기 때문에<br>
   " 이용성은 정상인가? 이 IP는 차단 대상인가? 패턴이 악성인가? 너무 많이 들어오나? " 등등의 판단을 할 수 있음.<br>
   트래픽을 통과 시킬지, 드롭할지, 다른 곳으로 보낼지 직접 제어 가능.

### 1-3 인라인 방식 왜 사용하나?

**1). 실시간으로 보안 적용하기 좋음.**
- 트래픽이 인라인 장비를 지나가기 때문에

**2). 트래픽 제어**
- IP기반 차단
- 포트 기반 제어 (ex 22번 SSH 사내망에서만 들어와야해)
- 프로토콜 제어 (HTTPS, DNS)
- Rate Limit
- 접근제어 (ex /admin 사내망에서만 들어와야해)

**3). 서버 보호**
- 인라인 장비가 서버 앞에 있으면 모든 요청을 서버가 처리하지 않아도됨. (Reverse Proxy)

### 1-4 대표적인 인라인 장비

**1) 방화벽**<br>
: 대표적인 인라인 장비

**2) 로드 밸런서**<br>
로드 밸런서는 들어오는 요청을 서버들에게 분배해주는 장비.

```
Client -> Load Balancer -> WAS A/B/C
```

### 1-5 장단점

**장점 :**
- 강제성 (모든 트래픽이 반드시 장비를 지나감)
- 실시간 차단, 서버보호 (악성 요청이 서버 도달전 막을 수 있음.)
- 정책 적용이 확실함 (우회 경로가 없음)
- 트래픽 제어 (Rate Limit, 필터링, 라우팅 제어가능)

**단점 :**
- 병목 현상 (외부 인터넷 → 인라인 장비 → 서버)
- 단일 장애 지점 (인라인이 죽으면 전체가 죽는다)
- 잘못된 정책이라 발생하는 설정 실수 영향이 상당히 크다.

**장애 극복 방법**
- 이중화 : Inline 장비를 2대 이상 구성
- failover : 장애 발생 시 대기 장비로 자동 전환
- Bypass Mode : 장비 장애시 트래픽 우회 동과시킴
- <span style="color:red">모니터링</span> : 지연, 차단수, 에러율, cpu/메모리 감시 **(중요 - 개발자가 하게되는 일.)**

### [헷갈리기 쉬운 것들]

**Q 인라인 방식은 장비 이름인가요?**
- 장비를 배치하는 방식
- 같은 방화벽이라도 트래픽이 무조건 통과하면 = Inline, 아닌 경우 = Out of Path

**Q Inline이면 무조건 좋은가? → no**<br>

- ☐ 인라인 장비가 장애나면 전체 서비스가 죽나?
- ☐ 인라인 장비의 처리량이 지나가는 트래픽을 감당할 수 있나?

# 2. Out of Path

실제 트래픽 경로 밖에서 트래픽의 복사본을 받아서 옆으로 보내는 방식 (ex) 침입 탐지 시스템)<br>
⇒ **주요 목적 : 보안 탐지, 네트워크 분석, 성능 모니터링**

📷 [이미지: Client → Switch/Router → Server / 트래픽 복사본 → 분석 장치 Sensor 다이어그램]

### 왜?

- **서비스 트래픽에 영향을 주지 않음.** (Out of path는 트래픽 경로 밖에서 동작함.) → 분석 장치가 고장나더라도 실제 처리 흐름에는 영향을 주지 않음. (인라인은 서비스가 죽음)
- <span style="color:red">모니터링이 안정적임</span> : 트래픽을 직접 건들지 않고 복사본이니까.
- 탐지와 분석에 집중 : 장비들에도 단일 책임원칙 같이 장비에서 하고 싶은 일이 별도로 정해져 있는 경우가 많음.
  - out of Path : 트래픽이 이상한데..? 한번봐줘 **(탐지 중심)**
  - Inline : 너 이상한데 **차단**

### Out of Path vs Inline

| 구분 | Inline | Out-of-Path |
|---|---|---|
| 위치 | 실제 트래픽 경로 위 | 실제 트래픽 경로 밖 |
| 원본 트래픽 처리 | 직접 통과시킴 | 복사본을 분석 |
| 차단 능력 | 직접 차단 가능 | 직접 차단은 제한적 |
| 서비스 영향 | 장비 장애 시 서비스 영향 큼 | Sensor 장애 시 서비스 영향 작음 |
| 주요 목적 | 제어, 차단, 필터링 | 탐지, 분석, 모니터링 |
| 대표 장비 | 방화벽, IPS, WAF, 로드밸런서 | IDS, SIEM, Zeek, Wireshark, Flow Logs |

# 4. WireShark

: 네트워크의 문제, 분석, 소프트웨어 및 통신 프로토콜 개발, 교육에 쓰이는 오픈 소스 패킷 분석 프로그램. **(보이지 않는 네트워크의 흐름을 눈으로 볼 수 있게하는 도구임.)**<br>
: 내 컴퓨터나 네트워크 인터페이스를 지나가는 패킷을 캡처하고 분석하는 네트워크 프로토콜 분석 도구.

네트워크 통신은 눈에 안보임.
- 브라우저 접속, 줌 사용 : 내부적으로는 상당히 많은 일들이 일어남.

```
브라우저 접속 -> DNS 조회 -> TCP 연결 -> TLS Handshake -> HTTP 요청 -> 서버 응답
```

**네트워크 캡처 도구를 왜 사용하나?**<br>
: 네트워크 문제를 확인해야하는 경우가 있는데 애플리케이션 로그는 볼 수 없음.

### 와이어샤크로 실제 볼 수 있는 것들

| 확인할 수 있는 것 | 예시 |
|---|---|
| DNS 조회 | 도메인이 어떤 IP로 해석되는지 |
| TCP 연결 | 3-way handshake가 성공하는지 |
| 재전송 | 네트워크 손실로 재전송이 발생하는지 |
| TLS Handshake | HTTPS 연결이 어디서 실패하는지 |
| HTTP 요청 | 평문 HTTP 요청/응답 내용 |
| 포트 통신 | 특정 포트로 패킷이 실제로 나가는지 |
| 응답 지연 | 요청 후 응답까지 시간이 얼마나 걸리는지 |

### 와이어샤크 사용법 - 필터

모든 네트워크 패킷을 다 보려고 하면 너무 많아서 → 내가 원하는 패킷만 골라 보는 기능.

- **Capture Filter** : 어떤 패킷을 저장할지 결정하는 필터. (`host 8.8.8.8`)
- **Display Filter** : 캡처한 다음에 어떤걸 보여줄지 정하는 필터. (`ip.addr = 172.168.0.1`)

→ 공식문서에서 doc를 보면 어떤 걸 할 수 있는지 나와져 있음.

## 용어정리

**Inline** : 네트워크 상의 데이터 패킷이 반드시 해당 장치를 통과하도록 설계된 네트워크 구조. 트래픽을 직접 제어(차단, 통과, 전달) 가능.<br>
**Out of Path** : 실제 트래픽 경로 밖에서 트래픽의 복사본을 받아 분석하는 방식. 탐지와 모니터링이 주목적.<br>
**방화벽** : 대표적인 인라인 장비. 트래픽을 필터링하고 차단하는 보안 장치.<br>
**로드 밸런서** : 들어오는 요청을 여러 서버에 분배해주는 인라인 장비.<br>
**WireShark** : 네트워크 인터페이스를 지나가는 패킷을 캡처하고 분석하는 오픈소스 네트워크 프로토콜 분석 도구.<br>
**Capture Filter** : 어떤 패킷을 저장할지 결정하는 와이어샤크 필터.<br>
**Display Filter** : 캡처한 패킷 중 어떤걸 보여줄지 정하는 와이어샤크 필터.<br>
**failover** : 장애 발생 시 대기 장비로 자동 전환하는 방식.<br>
**Bypass Mode** : 장비 장애시 트래픽을 우회하여 통과시키는 모드.
