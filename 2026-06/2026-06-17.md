# [한줄 정리]

- **ISP** : 인터넷을 제공하는 통신 회사 (KT, SKT..)
- **Proxy** : 클라이언트와 서버 사이에 중계자 역할을 하는 네트워크 장치, 익명성을 만들고 보안을 강화할 수 있음.
- **Reverse Proxy** : 서버 대신 클라이언트 요청을 받아 처리하는 방식 (NginX - 웹서버)
- **Forward Proxy** : 클라이언트 대신 외부 서버에 요청을 보내는 방식 (학교, 회사 네트워크, 응용계층 우회)
- **VPN** : 인터넷에서 지나가는 여러 공유기와 라우터를 거칠때 클라이언트랑 서버가 통신하는 내용을 별도로 한번더 감싸서 통신하는 방식. (물리적으로 떨어져 있어도 내부망을 안전하게 사용할 수 있음)
- **NAT** : 사설 IP와 공인 IP주소를 변환하는 기술.
- **Symmetric NAT** : 동일한 내부 IP, port를 사용해도 외부 대상에 따라서 매핑 IP, port별로 생성. (추적X)
- **Cone NAT** : 특정 내부 IP와 포트에 대한 NAT매핑 고정, 외부 IP에서 매핑이 접근 가능한 방식

# 1. 프록시

: 클라이언트와 서버 사이에서 중계자 역할을 하는 네트워크 장치. (Proxy = 대리인)

주의) 인라인 장비와 동일한 단점을 가지고 있음.<br>
실무에서는 보안성과 성능때문에 중간에 다른 서버를 하나 더 두는 경우가 많음.

```
client -> proxy -> server
```

**[동작 방식]**

1. 클라이언트가 Proxy에게 요청
2. Proxy가 서버에게 대신 요청
3. 서버가 Proxy에게 응답
4. Proxy가 클라이언트에게 응답 전달

**장점 :**

| 기능 | 설명 |
|---|---|
| **보안 강화** | 클라이언트와 서버의 직접 연결을 줄이고, 요청을 검사하거나 차단 |
| **트래픽 최적화** | 캐싱, 압축, 로드 밸런싱 등으로 성능 개선 |
| 접근제어 | 허용된 사용자나 IP만 특정 서비스에 접근하게 함 |
| **익명성** | 클라이언트의 실제 IP나 서버의 실제 IP를 숨김 |

**Proxy 종류**<br>
: 누구를 대신하냐에 따라서 종류가 나뉨 → 클라이언트 대신 vs 서버 대신

### 1-1. Forward Proxy

: 클라이언트 대신 외부 서버에 요청을 보내는 프록시.<br>
: "프록시야 나 대신 naver.com에 요청을 해줘"<br>
: 서버는 forward proxy인지 client인지 모르고 응답을 반환해주기 때문에 **"익명성"** 이 생김.

<img width="1212" height="754" alt="image" src="https://github.com/user-attachments/assets/5e11a897-25c0-44af-825c-bf4538b843c5" />


**사용 예시**
- 회사, 학교 네트워크 프록시 : 특정 사이트 접근 제한, 사용기록 관리.
- 익명 프록시, 제한 우회 : VPN으로 사용

### 1-2. Reverse Proxy

: 서버 대신 클라이언트 요청을 받아 처리하는 방식<br>
: 클라이언트는 실제 서버를 알지도 못하고 직접 접근도 못함. 대신 리버스 프록시에 요청함.<br>
클라이언트에게 뒤에 있는 서버를 숨길 수 있음.

<img width="1252" height="956" alt="image" src="https://github.com/user-attachments/assets/188b6b69-bbf4-4c0b-b561-5ef1f0311714" />


- **요청 라우팅** : /api 는 API 서버, /static은 정적 파일 서버로 전달.
- **로드밸런싱** : 여러 서버 중 하나로 요청을 분산함.
- **SSL/TLS 처리** : 모든 통신이 HTTPS이면 통신이 무거워짐. S를 때고 처리하는 걸 서버 대신 reverse proxy가 해줌. ⇒ HTTPS 인증서 처리, 백엔드 서버 부담 감소함.

**사용 예시**<br>
: 웹 서버 (NginX, HAProxy), CloudFront, API Gateway

**Forward Proxy VS Reverse Proxy**
- **Forward Proxy** : 클라이언트가 프록시를 통신전에 명시적으로 설정해야함.
- **Reverse Proxy** : 클라이언트는 서비스 주소만 알고 접속함.

클라우드 개발자 입장에서는 **Reverse Proxy가 훨씬 중요함.**

```
Client
  ↓
CloudFront / WAF
  ↓
ALB / Nginx / API Gateway  <- Reverse Proxy
  ↓
Spring Boot / Node.js Server
```

### 헷갈리는 부분

**Q1 Proxy는 보안 장비인가?**<br>
: 이건 아님. 요청과 응답의 중계자인데 보안 기능을 수행하도록 하는 것임

**Q2 Forward Proxy와 Reverse Proxy는 같은 장비 인가?**<br>
: 기술적으로 SW로 다 구현할 수 있음. 그래서 하나에서 리버스 프록시와 포워드 프록시 다 설정하면 두개 다 같은 곳에 있음.

**Q3 Reverse Proxy, Load Balancer은 같은 건가요?**<br>
: 완전히 같은 개념은 아니고 실무에서 하나의 웹서버(NginX)가 리버스 프록시와 로드 밸런서를 같이 수행하는 경우가 많음.

# 2. VPN

: 인터넷에서 지나가는 여러 공유기와 라우터를 거칠때 나랑 서버가 통신하는 내용을 별도로 한번더 감싸서 통신함.<br>
: Forward Proxy방식과 유사함.

단점) 키 파일을 탈취 당하면 내부망까지 접속이 가능해진다.

```
내 노트북 → (암호화된 VPN 터널) → VPN Server → 회사 내부망/인터넷
```

<img width="600" height="433" alt="image" src="https://github.com/user-attachments/assets/2004520d-1203-4aec-982e-1bfb1bb29fc1" />


### 2-1 왜?

`[ 내 노트북 → 공유기 → 통신사 ISP → 여러 인터넷 라우터 → 목적지 서버 ]`<br>
우리는 여러 네트워크 장비를 거쳐서 통신을 한다.<br>
ex) 기본적으로 공용 네트워크를 거치는데 그건 보안성이 낮음

**1. 원격지 안전하게 내부망을 사용해야할 때**
- 회사에서 접근하면 회사 네트워크가 내부 네트워크라서 상관 없지만
- 출장이나 재택 근무 같은 상황에서 VPN터널을 만들어서 회사 VPN Server와 연결함.

**2. 보안성 강화 = 익명성이 생긴다.**
- 내가 요청하는 도메인이 어딘지 안보여줄 수 있음.
- 외국 사이트에 대한 접근할 때 정책이 차단할 때
  - 넷플릭스 ← 한국에서는 서빙이 안된 서비스를 VPN으로 감싸면 VPN의 위치에 따라서 해당 국가에서 보낸것 처럼 위장됨.

**3. 물리적으로 떨어져 있는 사설망을 하나의 사설망처럼 묶을때도 사용됨.**<br>
본사, 자사 서버를 VPN으로 묶어서도 사용함.

### 2-2 VPN 핵심 구성 요소

| 구성 요소 | 설명 |
|---|---|
| **VPN Client** | 사용자의 PC나 스마트폰에서 VPN 연결을 시작하는 프로그램 |
| **VPN Server** | VPN 접속을 받아 인증하고 터널을 만들어주는 서버 |
| **VPN Tunnel** | 클라이언트와 서버 사이의 암호화된 가상 통로 |
| **인증 정보** | 계정, 비밀번호, 인증서, MFA 등 사용자 확인 수단 |
| **암호화 키** | 데이터를 암호화하고 복호화하기 위한 키 |
| **가상 IP** | VPN 연결 후 클라이언트에게 할당되는 내부망용 IP |
| **라우팅 정책** | 어떤 트래픽을 VPN으로 보낼지 결정하는 설정 |

### 2-3 VPN의 동작 흐름

```
1. VPN Client 실행
2. VPN Server로 연결 요청
3. 사용자 인증
4. 암호화 키 협상
5. VPN 터널 생성
6. 가상 IP 할당
7. 라우팅 테이블 변경
8. 트래픽 암호화 후 터널로 전송
9. VPN Server가 복호화 후 목적지로 전달
10. 응답도 다시 암호화되어 Client로 반환
```

### 2-4 터널링

: 원본 패킷을 다른 프로토콜로 감싸서 보내는 방식.<br>
전용 통로를 만드는 것 처럼 가상의 네트워크 경로를 하나 만들어서 안에서 통신함.

### 2-5 VPN 연결방식

1. **Full Tunnel** : 모든 트래픽을 다 보내는 방식
2. **Split Tunnel** : 사내망에 가야하는 트래픽만 VPN가고 나머지는 일반 인터넷으로 내보내는 방식.

**사용 예시**
1. 재택 근무자 git연결
2. 공용망에서 통신 암화화 하기 (익명성)<br>
   → 공격자에게 암호화된 패킷이 노출되는데 키가 없으면 암호화된 패킷은 못풀기 때문에 의미 없음.

### 2-6 실무적인 관점

1. **Bastion Server, Jump Server** (중간 서버들)<br>
   : SSH 연결을 통해 중간 서버를 거쳐 최종 목적지 서버에 접근하는 기술
   ```
   [ ISP(인터넷) → public network → private Network ]
   ```
2. 사내 API 테스트
3. admin페이지를 외부에서 접속해야할 때.
4. IDC와 AWS 연결해야할때 : LAN - (site to site VPN터널) - LAN 연결 함

### 2-7 자주 헷갈리는 것

**Q1 VPN쓰면 완전 익명성을 가지나요?**
- VPN 사업자는 통신내역을 다 볼 수 있음. 사용자 통신 내역을 판매하는 방식으로 수익을 얻음

**Q2 VPN이랑 HTTPS랑 똑같은거 아닌가요? → NO**<br>
**VPN** : 네트워크 수준의 트래픽을 보호함. (SSH, SCP, HTTP등등 여러 종류 보호)<br>
**HTTPS** : 웹 서버와 브라우저 사이트 HTTP트래픽만 보호

# 3. NAT

- 실무에서 많이 쓰임.

: 사설 IP와 공인 IP주소를 변환하는 기술.<br>
IPv4의 주소 한계가 있음. (40억개가 모자람) → 사설 IP를 사용함.

**사설 IP와 NAT의 등장**<br>
**공개 IP** : 인터넷에 등록되어 있어야 하는 IP 40억개로 제한됨. 비쌈<br>
**사설 IP** : 공개되지 않는 IP 제한이 거의 없음, 비용 없음.

<img width="1426" height="698" alt="image" src="https://github.com/user-attachments/assets/d8077059-a7d3-4bf6-8b33-8ade3ca28cf9" />


NAT table을 어떻게 남길거냐에 따른 방식 차이 : **symmetric NAT, Cone NAT**

### 3-1 Symmetric NAT

: 동일한 내부 IP, port를 사용해도 외부 대상에 따라서 매핑 IP, port별로 생성.<br>
<span style="color:red">같은 출발지라도 모든 요청마다 NAT table을 계속 만들어줌.</span>
<img width="1442" height="791" alt="image" src="https://github.com/user-attachments/assets/a5917327-ef05-41c9-911d-c4027a4fb43e" />


- 보안성 강화 : 항상 NAT table을 새롭게 적으니까 외부에서 내부로 임의 접근이 어려움. (특정 사람한테 응답을 못보냄)
- P2P 연결 제약이 생김, 비대칭 통신이 제한됨.

사용 예시) 기업 보안망, 정부 기관, 보안 강화 내부망

### 3-2 Cone NAT

: 특정 내부 IP와 포트에 대한 NAT매핑 고정, 외부 IP에서 매핑이 접근 가능한 방식.

<img width="1467" height="812" alt="image" src="https://github.com/user-attachments/assets/c1d92b07-b5b3-405d-9912-f98eb281ba0b" />


장점) 외부에서 누가 보냈는지 알 수 있음 (출발지는 알 수 있음)

### 3-2-1 Full Cone NAT

송신 데이터 기반으로 NAT테이블 생성함. 내부 클라이언트가 outbound요청을 한번이라도 수행하면 매핑 생성.<br>
이후 어떤 외부 ip, port 모두 매핑된 정보로 해당 클라이언트에게 패킷 전송 가능. **(NAT 방식 중 가장 개방적인 형태.)**

**특징**<br>
**-NAT매핑 정보만 있으면 외부 모든 장치가 내부 장치로 패킷 전송이 가능해짐.**<br>
-내부 클라이언트는 한번이라도 outbound 요청을 하면 외부와 자유로운 통신이 가능함.<br>
ex) 온라인 게임, 화상통화, P2P통신에 사용

**보안**<br>
- 허용범위가 넓어서 보안에 취약함 (비인가 접근 방식)
- NAT 장치가 외부 요청을 별도로 필터링 X

### 3-2-2 Restricted Cone NAT

**\*보통 이 방식 사용!**

: Full Cone NAT의 보안 문제를 개선한 방식<br>
**내부 클라이언트가 Outbound 요청을 보낸 외부IP에만 접근 허용 (외부 무작위 접근 X), 연결 효율성을 유지 하는 방식.**

**특징**
- 외부 IP기반으로 접근을 제한하고 송신 기록이 없는 외부 장치 요청은 차단함.
- 동일한 외부 IP라면 포트 번호 관계 없이 통신 가능.

**보안**
- Full Cone NAT에 비해 보안성이 높음.
- 동일한 외부 IP라면 포트 관계 없이 접근이 가능함. 일부 보안 취약점이 존재함.

### 3-2-3 Port Restricted Cone NAT

: 외부 IP + 포트 번호까지 있어야 매칭됨.<br>
: 내부 클라이언트가 아웃바운드 요청을 보낸 외부 IP와 포트가 정확히 일치해야 접근 허용함.

**특징**
- 금융 거래 서버, 기업 네트워크에 사용됨.

**보안**
- 허용 조건이 엄격해서 외부에서 내부로 임의로 접근할 가능성이 차단됨
- 외부 네트워크로부터 무작위 접근 가능.
- 실시간 통신에서는 추가적인 연결이 없으면 통신이 안됨.

### 퀴즈

**Q NAT는 어떤 문제를 해결하려 하나요?**<br>
: 공개 IP의 부족 문제 해결하기 위해 나온 사설IP와 공개IP를 연결시킴

**Q symmetric NAT과 Cone NAT의 핵심적인 차이는?**<br>
symmetric NAT : 매핑 재사용, 외부 접근 비교적 쉬움<br>
Cone NAT : 목적지별 매핑 사용, 외부 접근 어려움

# 4. 네트워크 모델

### 4-1 네트워크 프로토콜

: 데이터 전송을 잘하기 위한 네트워크 장치들의 약속

**\<주요 네트워크 프로토콜\>**

1. **TCP** : 신뢰성 있는 데이터 전송을 보장.
2. **UDP** : 비 연결성 프로토콜, 빠른 전송 + 속도 제공해서 스트리밍, 온라인 게임에 사용함.
3. **ICMP** : 네트워크 진단, 오류 메세지 전송 용도
4. **ARP** : IP주소 기반으로 mac주소 찾는 프로토콜

**\<응용 계층 프로토콜\>**

1. **HTTP, HTTPS** : 웹 브라우저 - 서버 간 사용
2. **FTP** : 파일 전송 프로토콜
3. **SSH** : 원격 접속 제공 프로토콜 (암호화를 통해서 기밀성 보장함)
4. **SMTP** : 이메일 전송을 위한 프로토콜

### 4-2 패킷

데이터를 한번에 스트림으로 보내려면 다른 클라이언트들은 한명이 통신이 완료될 때까지 기다려야함.<br>
패킷으로 쪼개서 보내면 대기 없이 많은 장비들이 통신이 가능해짐.

문제) 보내는 사람도 받는 사람도 패킷으로 처리하니까 복잡함 → 해결) TCP/IP로 패킷의 체계적인 데이터 전송을 보장함.

**TCP/IP 계층화** : 네트워크 통신의 복잡성을 각 계층별로 독립적으로 작용하도록 함.

- **응용 계층** : 메세지에 데이터를 담고 전송 계층으로 전달함.
- **전송 계층** : 메세지 데이터를 세그먼트로 자름 (자른 데이터 뒤에 필요한 헤더들을 붙임)
- **인터넷 계층** : 전달 받은 세그먼트에 목적지 IP, 출발지 IP를 헤더에 추가
- **네트워크 인터페이스 제공** : 물리적 네트워크로 전송하기 위해서 프레임 생성함. (MAC주소 헤더 추가)

# 5. CIDR

: 라우팅할때 트래픽 경로를 명확하게 지정하기 위해 네트워크 범위를 구분하는 주소 표준.

**IP주소 구성**

```
192.168.1.10 /24  // 겉으로 보면 숫자 4개
```

- **네트워크 영역** : 이 IP가 어느 네트워크에 속해 있는지 (192.168.1)
- **호스트 영역** : 그 네트워크 안에 몇번 장치인지 (10)

**서브넷 마스크 또는 프리픽스의 길이 지정**<br>
/24 : 앞에 24bit가 네트워크 영역.

```
00000000.00000000.00000000.00000000
```

### 네트워크를 나누는 방식

1. **클래스 방식** : A, B, C
   - A : /8
   - B : /16
   - C : /24
   - → 클래스로만 나누니까 호스트의 수가 완전 작거나 완전 커지기만 함.

**CIDR**<br>
: IP주소 뒤에 /숫자 를 붙여서 IP를 표현.<br>
서브넷 마스크를 클래스에 고정하지 말고 필요한만큼 알아서 네트워크 영역을 정하자.<br>
/8, /16, /24만 사용하지 않고 필요한 만큼 /20, /22 이런 방식으로 사용하기.

호스트 255는 브로드캐스트 주소임.

**서브넷팅** : 한 방에 여러개의 컴퓨터가 있을때 용도에 맞게 네트워크를 나누는 것.
- 외부에서 접근 가능한것 : **public subnet**
- 외부 접근 안되는 서버 같은 것 : **private subnet**

## 용어정리

**ISP** : 인터넷을 제공하는 통신 회사 (KT, SKT..)<br>
**Proxy** : 클라이언트와 서버 사이에서 중계자 역할을 하는 네트워크 장치.<br>
**Forward Proxy** : 클라이언트 대신 외부 서버에 요청을 보내는 프록시. 클라이언트의 익명성 제공.<br>
**Reverse Proxy** : 서버 대신 클라이언트 요청을 받아 처리하는 방식. 서버의 실제 IP를 숨김.<br>
**VPN** : 통신 내용을 암호화된 터널로 감싸서 보내는 방식. 물리적으로 떨어진 내부망을 안전하게 사용 가능.<br>
**VPN Tunnel** : 클라이언트와 서버 사이의 암호화된 가상 통로.<br>
**Full Tunnel** : 모든 트래픽을 VPN으로 보내는 방식.<br>
**Split Tunnel** : 사내망 트래픽만 VPN, 나머지는 일반 인터넷으로 보내는 방식.<br>
**NAT** : 사설 IP와 공인 IP주소를 변환하는 기술.<br>
**Symmetric NAT** : 동일한 내부 IP/port라도 외부 대상마다 다른 매핑을 생성하는 방식.<br>
**Cone NAT** : 특정 내부 IP/포트에 대한 NAT매핑을 고정하는 방식.<br>
**CIDR** : IP주소 뒤에 /숫자를 붙여 네트워크 범위를 유연하게 지정하는 주소 표준.<br>
**서브넷팅** : 용도에 맞게 네트워크를 나누는 것. (public subnet / private subnet)<br>
**Bastion Server** : SSH 연결을 통해 중간 서버를 거쳐 최종 목적지 서버에 접근하는 기술.
