## 주제 1: HTTP 자격 증명 헤더 (인증)

HTTP는 **stateless**라서 요청을 기억하지 않음. 보호되어야 하는 리소스(프로필 사진, 결제정보 등)는 헤더를 통해 인증과정을 거침.

- `WWW-Authenticate` : 서버 → 클라이언트 (서버가 발급하는 response header)
- `Authorization` : 클라이언트 → 서버

### Basic Authorization
기본 인증 방식으로 id, pw를 인코딩해서 사용하고 HTTPS TLS와 같이 사용함.
- 장점: 구현이 간단함
- 단점: 인코딩은 치환이랑 같은 거라 암호화가 아님. TLS가 풀린 구간이 한 번이라도 있으면 탈취당할 수 있음. 서버에 직접 입력값이 맞는지, 인증 성공 권한은 있는지 물어보는 게 서버 자원에 부담이 됨.
- 사용: 간단한 내부 시스템, 테스트

### Bearer Token
기존 방식의 문제점 : 매 요청마다 서버가 체크해서 서버에 부담이 된다. (자원을 많이 쓴다)

서버에서 요청을 보낼 때, http 헤더에 토큰을 포함시켜 인증하는 방식. → 마치 영화관 티켓 같음. (가지고 있으면 통과)

```
Authorization: Bearer <토큰>
```

흐름: (1) 최초 로그인 (id, pw) → (2) 서버에서 인증과정 수행 후 토큰 발급 → (3) 토큰을 클라이언트한테 보냄 → (4) 앞으로 인증, 인가 필요할 때 토큰 전송

- 장점: 토큰이 털려도 유저의 비밀번호는 보호됨. 범용성이 좋다(모바일, 웹 다 잘 작동). CSRF 예방
- 단점: 토큰이 탈취당하면 위험함(토큰의 관리 주체는 client인데 client는 보안에 신경을 안 씀). 토큰은 보관하기가 어려움.
  - → 해결을 위해 HTTPS에서 동작하고 토큰 유효기간을 상당히 짧게 선정하는 게 일반적임.
- 저장소: LocalStorage(XSS 취약), Cookie(CSRF 취약)
- 사용: 자체 토큰을 발급할 때 (카카오 api 토큰 발급해서 네이버 로그인 되게 할 때)

## 주제 2: JWT

### 왜 나오게 되었지?
일반 베어러 토큰의 한계 : 결국 서버에 보관해야 함(토큰 값)

→ 서버가 db를 안 뒤져도, 토큰 글자 자체에 유저 정보가 적혀 있고, 정보가 위조됐는지 아닌지까지 스스로가 증명할 수 있으면, 서버가 자원을 안 써도 되겠는데? : **JWT**

- 장점
  - (1) 완전한 무상태성 + 확장성
  - (2) DB 조회를 상당히 적게 함. 서명 검증만 CPU로 연산만 하기 때문에 DB에 읽고 쓰는 것보다 자원이 훨씬 작게 듦. 요청이 늘어나도 그냥 JWT 토큰 검증 시간만 듦.
- 단점
  - (1) 무효화가 어려움 → 따라서 실무에서는 Access Token과 Refresh Token 사용함.
  - (2) 네트워크 대역폭이 낭비됨. 내용이 많을수록 토큰의 길이가 길어져서 접속자 수가 늘어나면 과금이 많이 됨.

### JWT 구성요소
- **Header** : 토큰의 타입(typ), 서명에 사용된 알고리즘(alg)
- **Payload** : jwt 토큰에 담을 정보들이 있는 곳 (여긴 평문) - ex) iat: 토큰 발생 시간, exp: 토큰 만료 시간
- **서명 영역** : 토큰의 위조 유무를 검증. (인코딩 헤더 + 인코딩 페이로드 + 서버의 비밀키) → 지정된 알고리즘으로 암호화.

### RTR (Refresh Token Rotation)
Refresh token 재사용하지 않는 것. → 한 번만 쓰면 폐기하고 새 거 씀. (refresh token이 탈취당했을 때 해결하려고 쓰는 기술)

JWT가 무효화가 어려워서 실무에서는 나눠서 사용함.

| 구분 | Access Token (접근 토큰) | Refresh Token (재발급 토큰) |
|------|------------------------|--------------------------|
| 역할 | 실제 API 리소스에 접근하기 위한 출입증 | Access Token을 새로 발급받기 위한 인증서 |
| 수명 | 15분 ~ 30분 | 2주 ~ 1달 (비교적 길게 설정) |
| 저장 위치 | 프론트엔드 메모리(변수) 또는 LocalStorage 또는 HttpOnly 쿠키 | 서버 측 저장소(Redis 같은) 혹은 클라이언트 HttpOnly 쿠키 |
| 전송 빈도 | 매 API 요청마다 항상 보냄 (노출 위험 큼) | Access Token이 만료되었을 때만 딱 한 번 보냄 |

## 주제 3: API 서버를 만드는 방법 - 레이어드 아키텍처

관심사가 뒤섞이면 양이 많아지고 중복 코드가 증가함 → **책임분리**를 위해 레이어드 아키텍처 사용.

```
Client ↔ Controller (외부 입출력 관련 처리) ↔ Service (비즈니스 로직 처리) ↔ Repository (DB 접근 CRUD 처리) ↔ DB
              DTO ↔                          DTO/Entity ↔                        SQL
```

- **Entity** : RDB를 객체화한 것. (테이블 정의, 컬럼 매핑, 키 정의)
- **DTO** : 계층 간의 정보를 전달. (전달할 데이터 구조 정의)
- **Entity → DTO 변환** : 책임소재가 애매해서 → helper나 mapper 클래스로 둠.
- **필터/인터셉터** : 클라이언트가 보낸 데이터가 다 제대로 있나 확인. 매번 컨트롤러에서 확인하는 대신 사용.
- 패키지 구조는 정답이 없음. 프로젝트 크기, 필요에 따라 결정.
