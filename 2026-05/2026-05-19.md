### 주제 2: MVC / spring web MVC

- 역할이 Model, View, Controller로 나뉘는 패턴.
- 각 객체가 서로 필요한 기능을 사용할 수 있도록 DI를 통해 의존성을 주입받음. 

```text
MVC에서 controller부분)

DispatcherServlet : 요청 받음
↓
HandlerMapping : 이 요청은 누가 처리할래? OO이가 하면 좋겠다.
↓
HandlerAdapter :OO이 호출해.(필요한 메서드 호출)
↓
Controller) users/posts/comments 처리 핸들러 : OO일 처리중 (db조회, 로직 실행, 결과 반환)
↓
View Resolver : Controller가 반환한 결과 이름을 보고 실제 View 파일을 찾아줌
↓
View : 실제 화면 생성 (사용자가 HTML/Json등을 만들어 응답)
↓
DispatcherServlet : 최종 응답 반환.
```

스프링 MVC: MVC를 이용해서 웹 애플리케이션 구현을 위한 프레임 워크.

- model : 실제 필요한 비지니스 로직과 데이터.
- view : 사용자가 보는 화면
- Controller : 요청 처리, 모델과 뷰 연결 → 사용자 요청을 URL단위로 받고 model과 view을 연결함

### 주제 3: HTTPS

- 왜 사용할까? )초기 웹에서는 HTTP는 평문으로 보냈음. 당시 지식을 검색하려던 목적이 웹임 .
하지만 현재는 네이버인증, 결제, 자산확인 등등이 개인에 대한 중요한 정보를 다루면서 보안이 중요졌고 안전한 정보 전달을 위해.

<핵심>
- 인증 : 통신하는 상대방이 누군지 신원 확인
- 암호화  : 데이터를 읽을 수 없는 형태로 변환

```text
<TLS Handshack>

서버 → 인증 기관 : 서버의 공개키로 인증요청 

인증기관 : 인증서를 만들어거 개인키로 전자서명

서버 → 클라이언트 : 인증서 전달 

클라이언트 : 인증서 안의 서버 공개키 확인

클라이언트 → 서버 : 서버의 공개키로 암호화한 대칭키를 전달

서버 : 서버의 개인키로 복호화 하여 대칭키 얻음. 

<이후 통신과정 HTTPS 시작 >
```


<인증서의 내용>

- 서버의 공개키 (비대칭키로 서명된 )
- 인증 기관 정보 (동사무소 이름, 주소 )
- 인증기관의 전자서명 (인증 기관의 비밀키로 서명함)

## 한 줄 정리

Spring Web MVC : Model, View, Controller로  코드의 책임을 분리하는 MVC패턴을 웹 프레임워크에 적용한것으로 데이터,화면, 요청 처리를 분리해서 코드 관리가 쉬워 자주 사용됨. 

DispatcherServlet : 공통로직을 처리하는 서플릿으로 MVC패턴에서  요청을 담당할 컨트롤러를 찾아달라고HandlerMapping에게 명령어하거나 view에서 사용자가 원하는 것을 출력해주는 역할을 한다. 

대칭키 : 암호화와 복호화를 대칭키로 하는 방식이고 처리는 빠르지만 보안에 취약하다.

비대칭키 : 개인키와 공개키가 존재하며 공개키로 암호화한 내용은  개인키로만 복호화하는 방식이다. 공개키 기반 인증서를 통해 서버를 인증해줄 수 있다. 보안에는 뛰어나지만 처리속도가 느리다. 

HTTPS : HTTP의 응답과 요청을 암호화하여 주고 받는 통신 방식으로 이 과정을 위해서 TLS handshack과정에서 서버는 인증기관에 전달하고 클라이언트 인증기관의 공개키로 인증서를 검증한다.

## 질문/응답 

- Q 서블릿이 뭔가요?

서블릿은 HTTP 요청을 해석하고 응답을  만들어주는   java 클래스입니다. 

과거에는 개발자가 요청마다 직접 서블릿을 만들어 처리 했습니다.유저의 요청이 1000개라면 1000개의 서블릿을 만들어야 했습니다.

MVC가 등장하고 DispatcherServlet이라는 하나의 서블릿이 모든 요청을 먼저 받고 HandlerMapping을 통해 알맞은 Controller를 찾아 실행하는 방식으로 변경되면서 개발자는 controller의 비지니스 로직을 작성하는데 집중하게 되었습니다.


- Q HTTPS의 키교환 방식을 설명해보세요.(면접 빈출)

서버는 먼저 인증기관으로부터 공개키가 포함된 인증서를 발급받습니다. 
이후 TLS Handshake 과정에서 서버는 클라이언트에게 인증서를 전달하고 클라이언트는 CA의 공개키로 인증서를 검증하여 서버를 신뢰할 수 있는지 확인합니다.
 그 다음 클라이언트는 대칭키를 생성하고 서버의 공개키로 암호화해 전달합니다. 
 서버는 자신의 개인키로 이를 복호화하여 같은 대칭키를 획득합니다.
