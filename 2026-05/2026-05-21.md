## 주제 1: 상태 (stateful, stateless) 와  연결

### 상태
* http는 stateless함. 웹도 stateless함 (초기 컴퓨터 용량이 제한적이라 자원이 부족해 stateful하게 구현할 수 없었음)
* stateful : 기억 해줄게 (단골이라 이거 드실래요? 느낌)
* stateless : 누구세요? (키오스크)

#### stateful
* 나만을 위한 경우
* 장점 : 맞춤형 서비스 가능 , 복잡한 흐름제어 가능 -> 게임이나 채팅에서 사용
* 단점 : 서버가 상태를 계속 기억해야함, 사용자가 많아지면 돈이 많이 듦, 분산 시스템(서버가 나눠진 곳)에서 처리 힘듦.

#### stateless
* 모두를 위한 경우
* 장점 : 서버 부담이 적음, 확장이 편함. 처리속도가 빠름
* 단점 : 복잡한 요청에 보낼 정보가 많음, 사용자별 서비스는 어려움, 순서가 있는 경우 관리가 어려움.

### 연결
* connection oriented : 연결성 유지 (전화)
* connectless : 연결성 X

#### connection oriented
* 연결이 유지됨
* 동시에 여러명과 통신하기 힘듦.(자원 사용량이 늘어남)
* 실시간성을 보장해야하는 게임, 화상채팅 등등에서 사용.

#### connectless
* 문자 , 편지
* 한번 통신이 가면 통신을 끊음
* 연결 설정,해제가 없어서 매우 빠름.
* HTTP 는 connectless하고 stateless한 통신

## 주제 2: 인증과 인가, 쿠키와 세션

### 인증과 인가
* 인증 = 나 누구 입니다. 저 학생입니다.
* 인가 = 나 이거 해도 돼?
* 인증, 인가 사용 예 )
  * 브라우저 → 나 A야 여기 내 id랑 PW야 (인증) → 서버
  * 브라우저 → 교재 정보를 줘 (인가) → 서버

### 쿠키
* 쿠키: 브라우저에 부스러기를 남기는 것.
* 왜?) 서버에 저장할 내용은 아닌데 유저한테 개인화는 하고 싶으니까 유저 쪽 자원에 저장하자 (서버는 너무 비쌈)
* 쿠키는 노출되도 되는 자원만 저장함
  * 방문기록
  * 장바구니에 담는 것들
  * 노출해도 되는 것들
  * 언어설정
* 사용 예 ) 브라우저 (언어설정이 한국어 ) - 서버 (한국어 컨텐츠를 줘야지 )

### 세션
* 인증한 유저를 매번 인증하는게 힘들어서 인증을 빠르게 할 수는 없나?
* 사용 예 ) 브라우저 → 쿠키 (내 새션 ID는 247이야 ) → 서버 → 세션 db session ID 247 저장 (필요하면 빠르게 꺼내서 쓸 수 있음.)

## 주제 3: 프레임 워크와 라이브러리, API

### 프레임 워크와 라이브러리
* 프레임 워크 = 일관성을 제공 , 자율성이 낮고 규제와 규약이 있음.
  * 개발을 위한 구조와 규칙을 제공 → 개발과정이 단순화됨.(기본 구조 제공), 개발 속도를 높일 수 있음(기본 기능 제공), 여러명이 작업해도 일관적(기본 규칙 제공)
* 라이브러리 = 전문성을 제공, 자율성이 있음.
  * 빠른 개발 (이미 만들어준 코드), 높은 완성도(그거만 만들던 사람이 만든 코드)
  * 라이브러리 = 지도, 그래프, 수학, DB 연결 등등..

### API
* “우리한테 데이터를 받아가려면 이런 형식으로 보내주세요 “하는 설명서
* api를 통해서 이미 만들어진 다른 어플리케이션과 상호작용이 가능.
* 내가 만든 서버도 API를 제공.
* 내부 API ,외부 API가 존재함 (내부 API를 만들 때도 퀄리티를 높여서 만들어라)
* 코드는 공식 문서다
  * 가독성이 높아야 한다.
  * 코드의 의도를 상세하게 기록해야 함 (주석)
* 상황 예 (카카오 지도 라이브러리 - API로 연결 - 배달의 민족 앱)

## 주제 4: 페이징

### 페이징 개념
* 한정된 용량에서 데이터를 한번에 처리할 수 있는 크기(페이지)로 나눠서 페이지 단위로 처리하는 것.

### <사용자가 보는 방식에 따른 페이징 종류>
* 페이지 베이스 방식 : 사용 ) 게시판 , 카페 등등 컨텐츠가 여러개 있는 곳.
* 인피니티 스크롤 : SNS에서 많이 사용되는 방식으로 스크롤이 맨 아래 도착했을때 다음 페이지를 보내줘.

### <데이터를 어떻게 끊어올 것인가 기준 분류>
* offset based 방식
  * offset=건너뛰기.
  * limit= 가져올 양.
  * ex) offset=0, limit=5이면 0번지부터 5개 드릴게요란 의미.
  * 장점 ) 구현이 간단하다
  * 단점 ) 데이터가 많으면 느려진다. 데이터 변화가 많으면 중복이 생긴다. 
  * 중복이 왜 생길까? 중간 데이터에 변경이 생기면 이전에 이미 가져온 데이터도 새로운 곳에 포함이 되기 때문.
  * ex) 게시판이나 기사에 사용되는 방식
* key based
  * key : 데이터의 키 값(인덱스)를 기준으로 데이터 가져오기.
  * ex) 마지막 가져온 데이터 이후로 5개 가져와줘.
  * SNS 피드 같은데 많이 사용함.
  * 장점 ) 큰 데이터에서도 조회 속도가 빠르다. 데이터 추가,삭제 되어도 안정적임.
* cursor based
  * key based에서 마지막 본 id값을 클라이언트한테 보여주기 좀 그런데? → base 64를 통해서 직렬화 시키면 클라이언트에게 마지막 값을 숨기는 방식
* token based
  * 매번 직렬화 하는 것보다, 서버에서 마지막 본 값을 저장하는 방식.

### 퀴즈
* 쿠팡에서 검색시 사용하는 페이징 기법 : page based
* X에서 사용하는 페이징 기법 : 인피니티 스크롤
