## 주제 1: OOP 

**개념:** OOP의 고유 명사는 **현실 세계의 객체 개념을 기반으로 데이터를 속성(필드)과 기능(메서드)로 묶어 프로그램을 설계하는 패러다임**입니다.

* **객체:** 역할과 책임을 가진 주체 (누가 책임 질래? → A객체가 책임짐)
* **OOP:** 역할과 책임을 가지고 있는 주체의 협력으로 바꾸는 것

⚠️ **객체에 대해 오해하는 포인트:** 객체는 데이터를 담은 상자(X)  
* **ex)** 커피 ← 아이스 아메리카노 인 경우 다른 점이 ‘온도’ 밖에 없음. 좋은 설계가 아님.

```java

    protected String temperature = "HOT";
}

public class IceAmericano extends Coffee {
    public IceAmericano() {
        this.temperature = "ICE"; 
    }
}
```

**주방장과 웨이터의 예시** - 요리할 때 필요한 변수와 메서드는 주방장 책임.
```java
class Chef {
    private final String recipe = "미디엄 웰던"; // 내부 비밀
    private int meatCount = 10;                // 내부 비밀

    // 주방장이 외부에 제공하는 메서드, 요리를 하겠다.
    public Steak cook(Order order) {
        wash();
        validateMeat();
        this.meatCount--;
        return new Steak(recipe);
    }

    private void validateMeat() {
        if (meatCount <= 0) throw new IllegalStateException("재료 소진!");
    }
    
    private void wash() {
        // 요리하기 전에, 도구를 씻는다.
    }
}

class Waiter {
    private final Chef chef; // 의존성 
    
    /* 주입 
    public Waiter(Chef chef) {
        this.chef = chef; 
    }
    */

    public void serve(Order order) {
        Steak steak = chef.cook(order); // 난 주방장의 제공한 기능을 믿고 맡긴다
        System.out.println(steak.getName() + " 서빙 완료");
    }
}
```

## 주제 2: SOLID - SRP

> **핵심 개념:** 하나의 클래스가 하나의 역할과 하나의 변경 이유만을 가지도록 설계해야 한다.

**SOLID:** 유지보수성, 확장성 높이려고 만든 다섯가지 핵심 원칙
* **S (SRP):** 단일 책임 원칙 (클래스를 수정해야하는 이유는 한가지다)
* **O (OCP):** 개방 폐쇄 원칙 (확장은 열어두고 기존 코드 수정은 닫는다)

* **SRP의 장점:** 수정 범위의 최소화, 가독성
* **SRP의 단점:** 과하게 SRP를 지키면 클래스의 개수가 증가하고 설계 비용이 커질 수 있다.

## 주제 3: SOLID - OCP, DIP

### OCP (개방-폐쇄 원칙)
> **핵심 개념:** 소프트웨어의 기능 확장은 열어 있고, 기존 코드의 변경은 닫혀 있어야 한다.

* **개방:** 새로운 기능을 추가하거나 확장에는 항상 열려 있어야 함
* **폐쇄:** 그로 인해서 기존 코드가 수정되는 것에는 닫혀있어야 함.
* **목적:** 새 기능 추가시 이미 잘 돌아가는 예전 코드에 손대지 않게!

💡 **실무에서 OCP원칙이 중요한 이유:** 내가 개발하지 않은 코드가 프로젝트 안에 99%가 넘음.

<details>
<summary>💳 예시코드 - 결제 (클릭하여 펼치기)</summary>

### 잘못된 예) 결제 로직 추가 변경시 closed 위반

```java
public class PaymentService {

    public void processPayment(String method, int amount) {
        if (method.equals("NAVER_PAY")) {
            System.out.println("네이버페이 결제 로직...");
        } else if (method.equals("TOSS_PAY")) {
            System.out.println("토스페이 결제 로직...");
        }
        // 만약 카카오페이가 추가된다면?
        // 또 이 파일(기존 코드)을 열어서 else if를 추가해야 함. -> Closed 위반
        else if (method.equals("KAKAO_PAY")) {
            System.out.println("카카오페이 결제 로직...");
        }
    }
}
```

### OCP가 지켜진 예) interface 도입

```java
// 1. 결제라는 역할 (규격화된 USB 포트)
interface Payment {
    void pay(int amount);
}

// 2. 새로운 기능은 "클래스 추가"로 구현한다 (Open)
class NaverPay implements Payment {
    public void pay(int amount) { System.out.println("네이버페이 결제"); }
}

class TossPay implements Payment {
    public void pay(int amount) { System.out.println("토스페이 결제"); }
}

class KakaoPay implements Payment { // 새로 추가된 카카오페이
    public void pay(int amount) { System.out.println("카카오페이 결제"); }
}

public class PaymentService {
    private final Payment payment; // 특정 회사가 아닌 "역할"에 의존

    public PaymentService(Payment payment) {
        this.payment = payment;
    }

    public void process(int amount) {
        payment.pay(amount); // 다형성 
    }
}
```

### DIP (의존역전 원칙)
> **핵심 개념:** 상위 모듈(정책을 결정하는 코드)이 하위 모듈(세부 구현 코드)에 직접 의존하지 않고, 양쪽 모두 추상화(인터페이스나 추상 클래스)에 의존해야 한다는 객체지향 설계 원칙

* **상위 모듈:** 엔진은 동력을 바퀴에 전달한다.
* **하위 모듈:** 엔진이 가솔린 → 전기 모터로 변경됨.

<details>
<summary>⚙️ 예시 코드 - 가솔린이 전기로 변경 (클릭하여 펼치기)</summary>

**잘못된 코드**
```java
public class DrivingService {
    // 엔진 하나 바꿨는데 주행 서비스 코드가 통째로 깨지고 수정됨 (Inversion 실패)
    private ElectricEngine engine = new ElectricEngine();  

    public void drive() {
        engine.start();
        System.out.println("주행을 시작합니다.");
    }
}
```

**잘된 코드**
```java
// 1. 대원칙이자 역할인 "인터페이스"를 선언 (추상화)
public interface Engine {
    void start();
}

// 2. 가솔린과 전기는 이제 이 규격에 자신을 맞춤 (저수준이 추상화에 의존)
public class GasolineEngine implements Engine {
    public void start() { System.out.println("가솔린 엔진을 시동합니다."); }
}

public class ElectricEngine implements Engine {
    public void start() { System.out.println("배터리 전원을 켭니다."); }
}

public class DrivingService {
    // 특정 엔진 이름을 지워버림. 오직 Engine 역할에만 의존
    private final Engine engine;

    // 내가 직접 new하지 않고, 외부에서 주는 대로 받음 (의존성 주입)
    public DrivingService(Engine engine) {
        this.engine = engine;
    }

    public void drive() {
        engine.start(); // 어떤 엔진이든 start() 계약만 충족하면 실행 가능
        System.out.println("주행을 시작합니다.");
    }
}
```

## 주제 4: JVM

### JVM 구성
* **Class Loader, Execution Engine(JIT, Interpreter), Runtime Data Area**

<img width="1478" height="839" alt="image" src="https://github.com/user-attachments/assets/507f8f55-c768-4e2c-af1c-aae351fb6ca0" />

### 1. Class Loader
* 바이트 코드를 확인하고 Method Area에 올리는 역할.

| 구분 | 주요 내용 | 상세 설명 |
| :--- | :--- | :--- |
| **메타데이터** | 클래스, 인터페이스, 필드 | 해당 바이트 파일의 구조를 정의하는 기본 정보 |
| **상수 풀 (Constant Pool)** | 선언된 상수, 상수의 인덱스 | 프로그램 내에서 사용되는 리터럴 상수와 참조 정보 관리 |
| **메서드** | 실제 구현 로직 | 클래스 내부에 정의된 메서드의 실행 가능한 바이트코드 |
| **속성 (Attributes)** | 부가 정보들 (소스 파일 이름, 디버깅 정보 등) | 컴파일 및 디버깅 등에 필요한 추가적인 메타데이터 |

* **Constant Pool:** 바이트 코드 내부에 있는 테이블. 실행 중 필요한 이름과 참조를 인덱스로 관리함.

### 2. 실행 엔진 (Execution Engine)
* 메모리에 로드된 바이트 코드를 인터프리터나 JIT 컴파일러를 통해 기계어로 바꿈.
* **흐름:** Class Loader → Method Area → 
  * `Interpreter` (기계어로 실시간 변환) → OS → Hardware
  * `JIT Compiler` (자주 사용하는 걸 미리 컴파일해서 Native Code로 캐싱해둠) → OS → Hardware

### 3. Runtime Data Area
<img width="1312" height="797" alt="image" src="https://github.com/user-attachments/assets/f6859a37-6063-455e-9bc9-6a03fc897854" />

#### 📂 Method Area (메서드 영역)
* 정보들이 저장되는 전역 공간.
* JVM이 실행될 때 생성되는 공간.
* 바이트 코드를 처음 메모리 공간에 올릴 때 초기화 되는 대상.
* 프로그램 전역이 공유함.
* **저장 정보:** Constant pool, 필드나 메소드 데이터, 메소드 코드, 생성자 코드

#### 🥞 Heap과 Stack
* **참조형 종류:** 클래스, 인터페이스, Enum, Array
* **Stack:** 기본 자료형 데이터 보유, 참조형 데이터의 주소(참조값)만 가짐 | 스레드 마다 고유한 JVM Stack이 생성됨.
* **Heap:** 참조형의 실제 데이터가 생성되는 공간 (객체 저장소)

#### 💻 Native Method Stack
* 자바 코드가 아닌 C, C++, 어셈블리로 작성된 언어를 실행할 때 사용하는 스택 메모리.

    👉 컴파일 방식과 인터프리터 방식을 모두 사용하기 때문.  
  * **컴파일:** 자바 소스 파일(`.java`)이 컴파일러(`javac`)에 의해 중간 코드인 바이트 코드(`.class`)로 변환됨.  
  * **인터프리트:** 구동 시 바이트 코드를 JVM 내부 인터프리터가 한 줄씩 기계어로 번역하며 구동함. (속도 보완을 위해 핫스팟에 JIT 컴파일러 결합)
